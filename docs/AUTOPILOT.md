# 全自动开发与部署

在「全自动交付」输入应用名称、目标和验收标准，点击 **全自动开发并部署**。这一次启动授权涵盖规划、模型调用、自动修复、测试、部署及失败恢复；之后没有逐阶段确认弹窗。

## 自动执行链

1. 检查模型配置和 Docker Linux 容器可用性，环境缺失时在调用模型和创建项目之前停止。
2. 自动创建项目、拆解功能并按员工能力分工；已有项目则使用已保存的目标和任务。
3. 依次生成接口契约、后端、前端和集成测试。格式失败自动重试当前阶段，已有阶段从检查点读取。
4. Docker 构建生产镜像，使用临时独立数据卷、内部网络、非 root 运行用户和资源限制实测接口、随机 SQLite 业务数据、更新/删除、重启读回、浏览器表单和手机布局。未声明的修改或删除明确不在覆盖范围内。
5. 独立 AI 审查将每条需求关联到真实文件和通过的检查。失败项在约定次数内定点修复并重新测试，不能删改既有测试来假通过。
6. 自动发布门禁要求本版实际验证、浏览器检查及每条需求的支持证据全部通过。涉及真实支付、外部凭据、人工行为或缺少证据的要求停止发布并报告，不能假造验收。
7. 使用实测镜像的不可变 ID 发布，不重新构建另一份镜像冒充验证版本；在切换前停止旧容器，把静止的一致数据卷复制到新版本。启动新容器，检查健康接口和业务读取。启用 Caddy 时自动发布独立 HTTPS 域名并检查外部健康接口。
8. 新版失败则自动恢复旧容器和旧数据卷；正常部署后每 15 秒巡检，连续三次失败自动回滚上一版。失败版数据卷保留，便于提取切换后产生的数据。

「工程与测试证据」可随时查看源码、真实检查、AI 审查与历史记录。机器发布决定独立记录，**不会伪造人工验收通过**。业务语义与安全要求仍受声明测试及 AI 证据审查的覆盖范围限制，不保证任意复杂软件都能无人干预交付。

## 一次配置

推荐使用独立 Linux 服务器或虚拟机运行控制器，安装 Node.js 24、Docker Engine、完整 npm 开发依赖及 Playwright Chromium：

```bash
npm ci
npm run build
npx playwright install --with-deps chromium
docker info --format '{{.OSType}}'
```

Docker 最后一条应返回 `linux`。控制器需要 Docker CLI 和 Docker daemon 权限；应用容器不会挂载 Docker socket、宿主机目录、工作台密钥或控制器文件。Docker 构建需要联网拉取 Node 基础镜像和锁定 npm 依赖；运行后的应用使用内部网络，默认不能访问外部服务。

控制器本身管理 Docker，权限相当于服务器管理员，应运行在专用机器；不要把此权限授予生成代码，也不要把 Docker socket 挂进生成的应用。原有精简 Compose 工作台镜像没有 Docker CLI / Chromium，**不支持全自动控制器**；使用主机 Node 服务或专门的独立控制器机器。

后端代码在容器内执行；浏览器检查在控制器侧启动启用 Chromium sandbox 的全新无密钥上下文，拦截整个上下文（包含弹出页）的外域 HTTP 与 WebSocket，阻止 Service Worker / 下载并限制非代理 WebRTC UDP。浏览器自身漏洞和网络栈不受这些应用层路由的形式化保证，仍需专用机器、及时更新 Chromium 和主机出站防火墙；不能把路由拦截宣传为完整的浏览器操作系统网络隔离。Chromium sandbox 启动失败则验证失败，不通过关闭 sandbox 绕过。

Windows 可以使用已启用 Linux 容器的 Docker Desktop，并安装 Playwright Chromium；无需 Linux systemd 即可使用新增的 Docker 全自动实测流程。但这台当前工作电脑未安装 Docker，WSL 和 VirtualMachinePlatform 功能未启用（固件虚拟化已启用），因此目前只能显示缺失环境，不能冒充已完成实机自动部署。启用 WSL / VirtualMachinePlatform 或安装 Docker 往往需要系统重启，本次未擅自重启电脑。

### 自动发布公网 HTTPS

先完成 [工作台密码与 HTTPS](DEPLOYMENT.md) 配置。在同一 Linux 主机运行 Caddy，使用 [Caddyfile 样例](../deploy/autopilot.Caddyfile)，并将工作台域名和 `*.apps.example.com` 的 DNS 都指向此服务器。子域名各自通过 HTTP-01/TLS-ALPN-01 申请证书，不要求 DNS 插件。TCP 80/443 需可达。

控制器环境设置：

```bash
ARK_RELEASE_DOMAIN=apps.example.com
ARK_CADDY_ADMIN=http://127.0.0.1:2019
ARK_CADDY_SERVER=srv0
ARK_RELEASE_PORT=8800
```

Caddy 的管理接口保持本机监听。`srv0` 是该样例适配后的 HTTP 服务器 ID，已有复杂配置应先用 `caddy adapt --config ...` 确认对应 ID。控制器只插入和修改带 `ark-auto-*` ID 的应用域名路由，不覆写工作台或其他路由。应用域名稳定为 `app-<项目哈希>.apps.example.com`，升级和回滚端口保持不变。

Caddy API 更新会写入自动保存配置；后续服务启动使用 `caddy run --resume` 载入它，不能每次用原始 Caddyfile 覆盖动态路由。初次先加载样例生成配置，再启用恢复模式。Caddy 凭据或 TLS 权限问题会在自动发布日志中报告。

没有配置发布域名时仍自动部署到本机 `http://127.0.0.1:8800` 起的独立端口。公网绑定始终由可信控制器完成，模型不能执行任意 shell、设置监听端口或读取服务器密钥。

提供 [自动控制器 systemd 样例](../deploy/ark-autopilot.service) 和 [环境变量样例](../deploy/autopilot.env.example)。与基础工作台服务二选一。管理员需创建 `ark` 用户、数据目录并授予 Docker 访问，按样例在 `/opt/ark-browsers` 安装 Chromium、允许运行用户读取；根据实际 Node 路径调整 `ExecStart`。

## 重启、停止与更新

- 任务和部署元数据保存在数据目录的 `autopilot-jobs.json`、`autopilot-releases.json`。服务重启后，明确启动过且未停止的任务会自动从检查点继续，不再要求重复确认。当前阶段中断的一次模型请求可能已在服务商侧计费，重启后可能重做这一阶段；不会重做已完成阶段。
- 启动时未完成的部署会先恢复旧版；Docker 暂时不可用时每 15 秒自动重试恢复，成功后再继续已授权任务。旧版启动暂时失败的回滚也由巡检继续重试，无需反复手动重启控制器。
- 自动修复 0–2 次，额外自动恢复 0–3 次，均在启动时选定；已有单次请求超时/输出上限继续保留。没有新增累计 Token 预算熔断。
- 点击「停止任务」会中断当前模型/验证/部署阶段，保留源码和检查点；停止后的任务不会在重启时偷偷恢复。停止发布期间会恢复旧版，新版失败数据保留。
- 要更新已部署应用，在项目详情修改并保存目标/任务，然后在「交付项目」选择原项目，再次点击启动。会沿用已有工程基线和应用端口，自动测试并替换部署。
- 新版上线到发现故障之间可能已有新数据，回滚不会把新模式写入旧数据库，而是恢复切换前的旧卷；失败卷另存。需要时按业务规则提取其中的新记录。升级存在短暂切换停机，不承诺零停机。
- 受管容器名、镜像名、卷和网络均以 `ark-auto-` 开头并带标签 `ark.autopilot=1`。当前保留失败与历史版本，磁盘应监控；不自动删除生产数据卷。工作台完整备份不包含外部 Docker 数据卷与全自动元数据，请另外备份这些文件和应用卷。

## 验证

```bash
npm run check
npm run test:autopilot
```

`test:autopilot` 要求真实 Docker，不可用时失败，不将平台跳过视作通过。它验证真实镜像构建、随机数据持久化、浏览器交互、生产部署、卷复制与健康失败回滚；CI 已配置，当前 Windows 无 Docker，尚无本机真实通过结果。逻辑/API和页面测试使用模拟模型与 Docker 适配器，不能代替该实机套件或真实付费模型质量验收。
